# 架构说明

## 一、数据流

```
                ┌─────────────────┐
                │  每 60 秒 tick   │
                └────────┬────────┘
                         ▼
        ┌────────────────────────────────────┐
        │ 每个城市：读 plan 状态机            │
        │   idle  → 只在审查时刻动           │
        │   armed → 每分钟查分钟级            │
        └────────┬───────────────────────────┘
                 ▼
    ┌──────────────────────────────────────────┐
    │ 取数       和风 minutely / CN 3h / NMC    │
    └────────┬─────────────────────────────────┘
             ▼
    ┌──────────────────────────────────────────┐
    │ 判定       多源投票 + 实况交叉校验         │
    │            （和风说没雨、NMC 实测有雨也算）│
    └────────┬─────────────────────────────────┘
             ▼
    ┌──────────────────────────────────────────┐
    │ 出消息     降水提醒 / 雨停 / 预警 / 播报   │
    └────────┬─────────────────────────────────┘
             ▼
    ┌──────────────────────────────────────────┐
    │ 去重 → 冷却 → 发送 → 失败进 outbox        │
    └──────────────────────────────────────────┘
```

## 二、城市状态机

每个城市在 `state.json` 的 `plan` 里有一份独立状态：

```
            审查：无雨
   ┌─────────────────────────────┐
   │                             ▼
 idle  ──── 审查：有雨(时间 T) ──► armed
   ▲                               │
   │                               │ armed_at = T - 30min
   │                               │ 到点后每分钟查 minutely
   │                               │
   │      雨停（next60=0）          │
   └───────────────────────────────┘
```

| 字段 | 含义 |
| --- | --- |
| `mode` | `idle`（不查） / `armed`（每分钟查） |
| `armed_at` | 从这一刻开始查（未来时间就不查） |
| `alerted` | 这场雨已经喊过 |
| `rain_notified` | 已经推过「正在下雨」 |
| `last_scan` | 上次每日审查时间 |

**配额的关键**：`idle` 状态的城市一次分钟级请求都不发。

## 三、三级降级审查

```
省（省级信号）
  │  中央气象台该省全部城市站点 → 未来 48 小时有降水的比例
  ▼
市 / 区（投票）
  ├─ 和风 24h 逐小时     ┐
  ├─ 中国天气网 3 小时    ├─ 严格多数（过半）才算「有降水」
  └─ 中央气象台昼夜预报   ┘
  ▼
时间（取最早）
     多个源都判有雨 → 取最早的开始时间（宁可早报，不能漏）
```

**为什么取最早**：不同源对同一场雨的开始时间判断能差 20 分钟，取最早相当于「最急的那个源说了算」。

**省级只做必要性判断**：省里有雨不等于本市有雨，真正下单靠市级投票。

## 四、消息去重与冷却

| 机制 | 规则 |
| --- | --- |
| `sent_keys` | 每条消息有唯一 key（含城市+时段），发过就不再发 |
| 冷却 | 两次降水提醒最小间隔 `cooldown_minutes`（默认 5） |
| 播报去重 | `sent_briefs` 记录「哪个城市哪天哪一报」 |
| 补发队列 | 发送失败进 `outbox`，通道恢复后 60 分钟内自动补 |

## 五、告警分流

```
看门狗检测到异常
   ├─ 第三方 QQ(3001) 通 → 走第三方
   ├─ 不通 → QQ 官方机器人主动消息
   ├─ 失败 → config.alert 里的邮件/微信/钉钉/飞书
   └─ 全失败 → 只写日志，不重试（防刷屏）
```

## 六、可靠性设计

| 层 | 机制 | 触发条件 |
| --- | --- | --- |
| 进程退出 | 端口探测 → 重拉 | 端口不通 |
| **进程假死** | 心跳文件 >10 分钟未更新 → 杀进程重拉 | 主循环卡住 |
| 反复失败 | 三次上限 → 强制结束 → 写 `GIVEUP` 放弃 | 连续 3 次拉不起来 |
| 双开 | 端口独占绑定（`SO_EXCLUSIVEADDRUSE`） | 第二个实例自动退出 |
| 进程堆积 | pythonw 超过 4 个就停手 | — |
| 人为停止 | `STOP` 文件 | — |

**心跳必须由主循环写**：早期版本用独立线程写心跳，主循环卡死时线程还在跳，假死检测等于失效。

## 七、模块职责

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `rain_watch.py` | 主引擎：调度、取数、判定、文案、播报 | nmc / tier_check / ws_send |
| `cmd_listener.py` | 群指令、天气问答、城市管理 | rain_watch / city_cli / ws_send |
| `nmc.py` | 中央气象台：站点实况、官方预警、站点索引 | 无 |
| `tier_check.py` | 三级降级审查、多源投票 | nmc / rain_watch(取 3h 数据) |
| `qqofficial.py` | QQ 官方机器人 API | 无 |
| `qqbot_service.py` | 官方机器人遥控（WebSocket 常驻） | qqofficial / go.py |
| `alert.py` | 备用告警（邮件/微信/钉钉/飞书/Bark） | 无 |
| `watchdog.pyw` | 进程守护、假死检测、告警分流 | 各守护的端口 |
| `ws_send.py` | 极简 OneBot WebSocket 客户端 | 无 |

**循环依赖的处理**：`tier_check` 反向调用 `rain_watch.cn_hour3`，是运行时 import，不在模块顶层。

## 八、AstrBot 插件如何复用

```
astrbot_plugin_weather_watch/
  main.py          Star 类 + 发送桥接
  core/            原样复制的引擎（rain_watch/nmc/tier_check/cmd_listener）
```

关键一行：`rw.ws_send = AstrBotBridge(self)`

引擎里所有发送都走 `ws_send.send_group/send_private`，把它替换成 AstrBot 的
`context.send_message(UMO, ...)`，其余逻辑一行没改。

**没配 `push_targets` 时引擎不跑播报**，只提供指令查询，避免和独立版重复推送。

## 九、已知取舍

| 取舍 | 原因 |
| --- | --- |
| 分钟级只接和风 | 国内唯一能给出 15 分钟粒度的免费源 |
| 播报文案硬编码在 py 里 | 改起来要动代码，但比配置文件直观 |
| 冷却按时间不按事件 | 简单；代价是 5 分钟内的第二场雨会被压掉 |
| 省级扫描只看 48 小时 | 7 天窗口信号太糊（四川 80% 全「有雨」） |
